# 🥕 Food Supplier Finder

### AI-прототип сервиса поиска и сравнения поставщиков продуктов питания

> **Цель:** помочь менеджеру по закупкам быстрее найти подходящих поставщиков, собрать ключевую информацию и принять решение, с кем связаться.

---

## 1. Какие требования закрыты

| Что оценивается в тестовом | Решение |
|---|---|
| **Понятность идеи** | Один понятный сценарий: найти и сравнить поставщиков |
| **Логика работы** | Запрос → фильтры → релевантность → ranking → выбор → сравнение |
| **Удобство пользователя** | Естественный язык, фильтры, сортировка, карточки и Head-to-Head |
| **Качество прототипа** | Полноценный работающий Streamlit-интерфейс |
| **Полнота информации** | Цена, MOQ, заказы, документы, доставка, регион, контакты, сайт и источник |
| **Обоснованность реализации** | Гибридный поиск: lexical + semantic + business ranking |
| **Практическая применимость** | Сервис рассчитан на реальный сценарий менеджера по закупкам |

# 2. Пользовательский сценарий

Менеджеру не нужно разбираться в формуле рейтинга.

Он может написать обычным языком:

```text
органические томаты оптом для ресторана в Москве
```

или использовать только фильтры:

```text
Категория → Овощи
Город → Москва
```

Результаты появляются сразу после выбора фильтра.

После этого пользователь может изменить порядок отображения:

- рейтинг — выше / ниже;
- минимальный объём заказа — меньше / больше;
- цена — ниже / выше;
- количество выполненных заказов — больше / меньше.

Отдельно система определяет **лучший вариант** и подсвечивает его независимо от выбранной сортировки.

---

# 3. Почему используется semantic search

Для закупок недостаточно только точного совпадения слов.

Например:

```text
свежие томаты для ресторана
```

и

```text
свежие помидоры для HoReCa
```

могут описывать одну потребность.

Поэтому запрос и карточки поставщиков преобразуются в embeddings и сравниваются по смысловой близости.

### Используемая модель

```text
sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2
```

Она подходит для русскоязычных запросов и небольшого демонстрационного проекта.

---

# 4. Почему поиск гибридный

Чистый semantic search может вернуть тематически близкого, но товарно нерелевантного поставщика.

Например:

```text
Запрос: капуста
```

не должен приводить к поставщику круп только потому, что темы «продукты питания» близки.

Поэтому используется гибрид:

```text
                    Запрос
                       │
            ┌──────────┴──────────┐
            │                     │
      Lexical match        Semantic similarity
            │                     │
            └──────────┬──────────┘
                       ↓
                Product relevance
                       ↓
                    Ranking
```

Если в каталоге есть поставщики с явным соответствием товару, нерелевантные поставщики исключаются. Semantic similarity используется для ранжирования уже релевантных кандидатов.

Это делает поиск более предсказуемым для закупочного сценария.

---

# 5. Как определяется лучший поставщик

Пользователь **не вводит веса самостоятельно**.

Внутри сервиса оцениваются несколько групп факторов:

```text
Соответствие товару
        +
Коммерческие условия
        +
Логистика
        +
Полнота данных
        ↓
  Internal score
        ↓
     Rating 1–5
```

Пользователь видит только результат:

> ⭐ Лучший вариант

Внутренняя формула не перегружает интерфейс и не заставляет менеджера вручную настраивать ML-параметры.

# 6. Что получает менеджер

### Основные данные

- название;
- категория;
- город;
- регион;
- описание товара.

### Закупочные данные

- рейтинг 1–5;
- количество выполненных заказов;
- минимальный объём заказа;
- ориентировочная цена.

### Операционные данные

- сертификаты;
- доставка;
- регион работы.

### Контакты

- контактное лицо;
- телефон;
- email;
- сайт;
- источник информации.

### Дополнительно

- комментарии / заметки.

# 7. Head-to-Head comparison

В режиме сравнения поставщики отображаются рядом в отдельных колонках.

```text
┌────────────────┐  ┌────────────────┐  ┌────────────────┐
│ ★ Лучший       │  │ Поставщик B    │  │ Поставщик C    │
│ Поставщик A    │  │                │  │                │
│                │  │                │  │                │
│ Рейтинг 4.8    │  │ Рейтинг 4.6    │  │ Рейтинг 4.2    │
│ Заказов 615    │  │ Заказов 420    │  │ Заказов 280    │
│ MOQ 50 кг      │  │ MOQ 100 кг     │  │ MOQ 500 кг     │
│ 145 ₽/кг       │  │ 138 ₽/кг       │  │ 155 ₽/кг       │
│                │  │                │  │                │
│ ✅ Сертификаты │  │ ✅ Сертификаты │  │ ❌             │
│ 🚚 1–2 дня     │  │ 🚚 1–2 дня     │  │ 🚚 3–5 дней    │
│ ✅ Умеренный   │  │ ✅ Умеренный   │  │ ❌ Большой MOQ  │
└────────────────┘  └────────────────┘  └────────────────┘
```

Такой формат выбран вместо сухой таблицы, потому что менеджеру проще быстро сравнивать ключевые параметры «голова к голове».

# 10. Основные технологии

## Python

Основной язык проекта.

Использован потому что он удобен для сочетания data processing, NLP/ML и быстрого прототипирования.

## Pandas

Используется для нормализации, фильтрации и работы с каталогом поставщиков.

## Sentence Transformers

Используются для semantic search и embeddings.

Преимущество — можно применить готовую multilingual-модель без обучения собственного NLP-модуля.

## scikit-learn

Используется для fallback-поиска на TF-IDF, если embedding-модель недоступна.

## Streamlit

Используется как UI-слой.

Плюсы для тестового:

- быстрое создание рабочего прототипа;
- не требуется отдельный frontend;
- удобно демонстрировать data/AI-продукт;
- приложение легко запустить одной командой.

# 11. Почему не PostgreSQL / pgvector

Для production каталога поставщиков разумным следующим этапом является переход:

```text
CSV
 ↓
PostgreSQL
```

и:

```text
in-memory embeddings
 ↓
pgvector / Qdrant
```

Но для текущего тестового это сознательное упрощение.

В задании основное внимание уделяется понятности идеи, логике работы, удобству пользователя, качеству прототипа, полноте информации, обоснованности реализации и практической применимости.

Поэтому я не добавлял обязательную внешнюю БД и отдельный vector service, чтобы:

- прототип запускался без дополнительной инфраструктуры;
- HR мог открыть demo без развёртывания PostgreSQL;
- основная ценность решения оставалась в поиске и decision support.

При росте каталога архитектура позволяет вынести хранение и vector search в отдельные сервисы.

---

# 12. Почему нет web search

Поиск поставщиков в интернете расширил бы продукт, но создал бы дополнительные проблемы:

- разная структура сайтов;
- дубликаты;
- неполные данные;
- нестабильная доступность источников;
- необходимость проверки и нормализации информации.

Для тестового выбран контролируемый демонстрационный каталог.

Следующий этап может выглядеть так:

```text
Local catalog
      +
External search
      ↓
Normalize
      ↓
Deduplicate
      ↓
Rank
```

# 13. Что можно масштабировать дальше

### Data layer

```text
CSV → PostgreSQL
```

### Vector layer

```text
in-memory embeddings → pgvector / Qdrant
```

### Backend

```text
Streamlit → FastAPI → Search service
```

### AI comparison

```text
rule-based explanation → LLM-generated explanation
```

Эти изменения относятся к следующему этапу продукта и сознательно не включены в базовый тестовый прототип.
